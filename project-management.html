Case Study Plan: Managing a Software Database for an Educational Institution

Shanzay Khan · Professor Kiersten Cox · 27 September 2026

Introduction

Academic institutions rely on a large number of software applications to support teaching, research, administration, student services, finance, communication, and information technology. As the number of applications grows, it becomes essential for an institution to maintain accurate information about the software it owns, where that software is installed, which departments use it, which versions are in use, and what licensing agreements apply. This case study examines the development of a centralized software-tracking database for a fictional university. The database will be administered by the Information Technology (IT) department and will provide authorized staff with a reliable means of tracking software across the institution.

The project team will consist of a project manager, a database developer, a systems analyst, IT technicians, an information security representative, and representatives from selected university departments. The project will follow the six phases of project management proposed by Baars: initiation, definition, design, development, implementation, and follow-up. Each phase serves a distinct purpose, and according to Baars, clearly defining a project before implementation reduces misunderstandings and uncontrolled changes.

Project Management Plan

Initiation Phase

The initiation phase will establish the university’s need for a software-tracking database and assess the feasibility of the project. Baars identifies several steps in this phase: exploring the project idea, evaluating feasibility, identifying participants, defining expected results, and establishing project boundaries. The project manager will begin with preliminary discussions with the university’s IT director and representatives from key departments to identify current problems with software tracking. These problems may include the absence of a central software inventory, outdated or obsolete software versions, uncertainty about license expiration dates, duplicate software purchases, and limited knowledge of which applications are installed on which computers.

The project manager will then prepare a project proposal that documents the project’s purpose, expected benefits, initial scope, resource estimates, stakeholders, and preliminary risks. The database will be designed as a working institutional system rather than a prototype. The initial scope will include software name, software category, developer or vendor, current version, previous version, license type, license quantity, purchase or renewal date, installation date, department, computer or device, and the responsible IT staff member. Other IT asset management functions that are not directly required for tracking software, such as the management of printers, network equipment, and personal employee devices, will be excluded from the initial scope.

The project manager will lead this phase, and the IT director will serve as project sponsor. The database developer, systems analyst, IT technicians, department representatives, and information security representative will serve as project stakeholders. The deliverables of this phase will be an approved project proposal and an initial project plan. The university will then determine whether it has the resources, technical capability, management support, and time required to proceed. Establishing clear boundaries at this stage is important because an expanding scope can delay the schedule and reduce the likelihood of achieving the original goal (Baars).

Definition Phase

The definition phase will determine precisely what the database must do. According to Baars, requirements should be defined as clearly and completely as possible during this phase, and the expectations of all parties should be taken into account. These requirements include functional requirements, operational requirements, preconditions, and design constraints.

The systems analyst will conduct interviews and meetings with IT personnel, department administrators, software users, purchasing staff, and information security staff. The team will be responsible for identifying the information that must be captured for each software product. For example, each record may include the software name, developer, category, version number, licensing model, license count, license expiration date, departments using the software, installation location, computer identification number, installation date, and the staff member responsible for the software. Authorized users must also be able to search and update records and generate reports.

Security and operational requirements will also be defined. Because the database will contain information about institutional computers and software licenses, access will be restricted according to staff responsibilities. User roles will be identified, including database administrator, IT technician, department representative, and read-only manager. The team will also define backup requirements, data accuracy standards, and a process for correcting inaccurate data.

The proposed requirements will be distributed to stakeholders for review. This step is especially important because users should be consulted from the outset of a project rather than after development is complete (Baars). The deliverable of this phase will be an approved requirements document containing the functional and operational requirements for the database. Any conflicting requirements will be discussed and resolved before the project moves into the design phase.

Design Phase

During the design phase, the project team will determine how the requirements identified in the definition phase will be translated into the structure and functionality of the database. Baars describes this phase as the point at which one or more possible designs are developed and a final design is selected for development.

The database developer and systems analyst will create a preliminary data model that illustrates the structure of the database and the relationships among its data. Separate but related tables may be created for software products, developers or vendors, software versions, software licenses, departments, computers, and software installations. This structure will reduce redundant data. The team will also design user forms for entering and updating information, as well as reports that IT staff can use to track licenses, versions, and installations.

Several design options may be considered. One option is a basic database with limited reporting capabilities; another is a more detailed design that captures the relationships among software, computers, departments, licenses, and installations. The project team will evaluate these options based on usability, security, scalability, cost, maintenance requirements, and compatibility with the university’s existing IT infrastructure. A small prototype may be developed to demonstrate how users will enter and retrieve data.

The proposed designs will be reviewed by the project manager, database developer, systems analyst, information security representative, and selected end users, and their feedback will be incorporated before the final design is approved. The primary deliverable of this phase will be an approved database design that specifies the data structure, relationships, user roles, forms and reports, security strategy, and technical implementation. By the end of this phase, any major design conflicts should be identified and resolved.

Development Phase

The development phase will prepare all necessary components for implementing the database. According to Baars, this phase involves scheduling, acquiring required materials or services, assembling staff, and ensuring that all team members understand their roles before implementation begins.

The project manager will develop a detailed schedule and work breakdown structure covering database development, testing, data preparation, security configuration, user training, and deployment. Each team member will be assigned specific duties and responsibilities. The database developer will build the database according to the approved design, and the systems analyst will monitor development to ensure that it meets the documented requirements. IT technicians will compile a sample list of software and computers that can be imported or entered manually into the database.

The team will also establish a testing approach during this phase. Testing will cover a range of software products and versions, license types, departments, and computers. The team will develop test cases for creating, updating, searching, and reporting on records. Security testing will verify that each user role has access only to the appropriate information and functions. Backup and recovery procedures will also be developed.

A small group of IT staff and department representatives will be selected to serve as the pilot test group. Training materials, user guides, and technical documentation will be prepared before implementation. The deliverables of this phase will include the completed database, test plan, sample data, security configuration, implementation schedule, and user documentation and training materials. This phase will be considered complete when the team is ready to implement and test the system in the university’s environment.

Implementation Phase

The implementation phase is when the database is put into use as the primary outcome of the project. Baars describes this as the phase in which the actual project result is produced and then verified against the requirements and the approved design.

Implementation will begin with a controlled pilot before the database is rolled out across the entire university. The pilot will include the IT department, the business administration office, and a small number of academic departments. Existing software information from these departments will be entered into the database, and IT staff will verify software versions, license details, installation dates, and computer assignments.

The pilot will evaluate the database’s functionality, accuracy, usability, security, and performance. Users will create and update software records, search for installations, review license information, and generate reports. The project team will also confirm that users with different permission levels can access only the functions appropriate to their roles. Backup and recovery procedures will be tested to confirm that data can be restored in the event of a system failure.

Any issues identified during the pilot will be documented and resolved. For example, if department staff find that an important field is missing from software records, the project manager will determine whether the omission is an error or a formal change request. Baars emphasizes that once requirements and the design have been finalized, any changes should be discussed with the appropriate decision makers and documented to prevent later misunderstandings.

Once the pilot has been successfully completed and approved, the system will be rolled out to the remaining departments. IT staff will receive training, and departments will be given guidelines for keeping software information current. The implementation phase will conclude when the completed database meets the agreed-upon requirements and design.

Follow-Up Phase

The follow-up phase will ensure that the database continues to operate effectively after implementation. As Baars notes, this phase may include documentation, user training, help-desk support, maintenance, project evaluation, project reporting, and transfer of the system to the organization.

The project manager will conduct a formal review with the IT director and key stakeholders to determine whether the project goals have been met. The review will assess the accuracy of the data in the database, the ability of users to complete required tasks, the effectiveness of security controls, and the usefulness of reports for software management. Feedback will also be gathered from IT administrators and department heads.

Responsibility for the database will then be transferred to the university’s IT department. A designated database administrator will be responsible for maintaining the database structure, access rights, backups, and system performance. IT technicians will update records to reflect software updates, version changes, and device information. Departments will be required to notify IT when software is installed, removed, or replaced.

The university will also establish a regular review process, which may include quarterly reviews of software records and ongoing monitoring of license expiration dates. Regular database backups and periodic reviews of access rights will also be conducted, and user documentation and training materials will be updated as needed. Finally, the project manager will prepare a final project report that describes the project’s results, challenges, solutions, lessons learned, and recommendations for future projects. Once the database has been successfully transferred to the IT department and all project deliverables have been accepted, the project team will be formally released.

Conclusion

A centralized software-tracking database will give the university an organized system for managing information about its software, licenses, versions, departments, computers, and installations. However, building the database alone will not ensure the project’s success; effective management of requirements, stakeholders, resources, testing, implementation, and maintenance will be essential. Baars’s six-phase project management model provides a structured approach to these activities. The initiation phase establishes the project’s purpose and feasibility, the definition phase clarifies its requirements, the design phase defines the database structure, the development phase prepares the resources and the database for implementation, the implementation phase delivers and verifies the system through a pilot and a university-wide rollout, and the follow-up phase transfers responsibility to the IT department and establishes ongoing maintenance. By completing each phase in sequence and involving key stakeholders throughout the process, the university can develop a software-tracking system that meets its operational needs and provides a strong foundation for future maintenance and improvement.
